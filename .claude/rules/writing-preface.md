# 머릿말 규칙

머릿말은 챕터와 다르다. 이야기 파트/기술 파트 구분 없이, **독자에게 직접 말하는 단일 톤**으로 쓴다.

## 역할 분담

| 파트 | 역할 | 톤 |
|------|------|-----|
| 프롤로그 | 저자(캐릭터)의 성장 이야기 | 소설 내러티브 |
| **머릿말** | **왜 이 기술들을 배워야 하는가** | **독자에게 말하듯 대화체** |
| 맺음말 | 독자에게 보내는 마지막 메시지 | 대화체 |

## 문단 패턴

각 기술을 소개하는 문단은 이 흐름을 따른다.

```
(현실 상황) → (기술 이름 볼드) → (왜 필요한가 한 문장)
```

예시:
> 서버가 한 대일 때는 세션을 메모리에 두면 됩니다.
> 그런데 트래픽이 늘어서 서버를 두 대로 늘리면,
> 한쪽에서 로그인한 사용자가 다른 쪽으로 넘어갈 때 로그인이 풀립니다.
> **Redis**는 이런 상태 공유 문제를 해결하는 가장 흔한 선택지입니다.

## 머릿말에서 하지 않는 것

- 코드 블록
- 비유 (머릿말 본문은 비유 대신 현실 상황으로 설명. 단 저자별 섹션은 비유 허용)
- 저자 경험담 (프롤로그가 담당)
- 기술별 번호 매기기 ("1장은..., 2장은...")
- 감사 인사

## 저자별 독립 섹션 (공저일 때만)

머릿말 본문(훅 → 기술별 필요성 → 마무리) 뒤에 **저자 수만큼 독립 섹션**을 둔다. 단순 인사·소감이 아니라 "왜 이 책을 배워야 하는가"를 **저자마다 다른 관점**으로 풀이한다.

### 형식

- H2 헤더에 **이름만** 표기 (직책·소속·기여 영역·"대표저자" 라벨 모두 금지)
- 본문 1~2문단 (대표저자는 2~3문단)
- 본문 끝에 빈 줄을 두고 이름 단독 서명
- 저자 순서는 `answers.md` 기록을 따른다 (첫 번째 = 대표저자, 별도 라벨 없이 순서가 곧 표시)

### 관점 분담

저자가 N명이면 N개의 다른 관점으로 책의 필요성을 풀이한다. 자주 쓰는 분담 축:

| 관점 | 다루는 것 |
|------|----------|
| **시사점·시장** | 산업 변화·트렌드·시장 위상. 왜 "지금" 이 기술인가 |
| **정책·사회** | 조직·정보 비대칭·접근성. 누구를 위한 기술인가 |
| **기술** | 손으로 만드는 가치·블랙박스 해체. 어떻게 깊이가 생기나 |

3인 공저면 위 3축이 자연스러운 분담. 다른 분담 축(예: 교육·역사적·철학적)도 가능하지만 **저자마다 반드시 달라야** 한다.

### 비유 허용

머릿말 본문은 비유 금지(현실 상황으로 설명)지만, **저자별 섹션은 비유 허용**. 자기 관점을 한 가지 비유로 풀어 색깔을 만든다.

### 분량

- 대표저자(첫 번째) ≈ 다른 저자의 1.5~2배
- 전체 저자 섹션 합계 ≈ 0.5~1페이지
